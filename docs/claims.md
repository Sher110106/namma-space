# Claims ledger

Use a claim only when its evidence file exists and its value is measured. If it does not, use the fallback wording.

| Claim | Evidence | Fallback wording |
|---|---|---|
| Phone video only, with measured fidelity | `report.json`; `50_train/`; `60_export/export.json`; `eval/results/mushroom_*.json`; `eval/results/mip360_room.json`; viewer reality check | “Phone video input; we report held-out image scores and public-room checks.” |
| Close to LiDAR | `eval/results/mushroom_*.json`, with phone-only F-score at the required threshold beside the LiDAR baseline | **Threshold not met (re-checked 30 Oct 18:00 on the default pipeline, runs fix-honka and fix-vrroom): ours/LiDAR F@5cm = 0.519/0.803 = 65% on honka, 0.401/0.737 = 54% on vr_room; the rule needs 80%. An older honka run with the depth-loss variant r1 reached 0.630 (78%), still under the bar.** Use the fallback: give both numbers side by side with no adjective, e.g. “On the public honka room, phone-only geometry scores F@5cm 0.52 against 0.80 for iPhone LiDAR fusion (same fusion and crop). Before scoring, we fit our camera path to the dataset’s camera path (rotation, offset and scale). That fit removes our own 3.3% scale error, which we report separately.” State the vr_room pair (0.37 against 0.74, 3.1%) beside it, so the better room does not stand alone. Ours/LiDAR is 78.5% on honka and 49.9% on vr_room (from the JSON). |
